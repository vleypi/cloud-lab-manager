# cloud lab manager

Сервис, который выдаёт студентам облачные лабораторные стенды и сам проверяет их настройку. Работает поверх платформы «Кибер Инфраструктура» (OpenStack) и подключается к Moodle.

Проект сделан на хакатоне по кейсу «Автоматизация работы с лабораторными стендами».

## О приложении

Студент открывает задание в Moodle и получает свою виртуальную машину с консолью прямо в браузере. Сервис следит за загрузкой облака, сам удаляет истёкшие стенды и по SSH проверяет, правильно ли студент настроил машину. Преподаватель управляет пулом, курсами, лимитами и видит все стенды в админке.

## Архитектура

### Компоненты

```
браузер, Moodle
       |
     Nginx :8080 ── /api, /docs, WebSocket консоли
       |
       +── web     интерфейс на Next.js
       +── api     FastAPI ──────────── PostgreSQL
       |             |                  Redis
       |             +── guacd          консоль SSH, VNC, RDP
       +── worker  Celery ───────────── OpenStack API
       +── beat    расписание очистки   SSH к машинам студентов
```

`api` принимает запросы интерфейса и Moodle, хранит данные в PostgreSQL и ставит долгие операции в очередь. `worker` создаёт и удаляет машины в облаке и выполняет проверки, `beat` раз в заданный интервал запускает очистку. Redis служит брокером очередей и хранит временные ключи доступа и состояние входа через LTI. Наружу открыт только Nginx.

### Пул проектов

Сервис не создаёт проекты в облаке на лету, поэтому ему не нужны права суперадминистратора. Проекты готовятся заранее и описываются в `config/pool.yaml`, их можно также добавить через API или найти автоматически в облаке. Каждому студенту выдаётся один свободный проект. Выдача атомарная, второй активный стенд тому же студенту запрещён на уровне базы данных. После удаления стенда проект возвращается в пул.

### Жизненный цикл стенда

```
allocating → deploying → ready ⇄ frozen
     |           |         |        |
     +───────────+─────────+────────+──→ cleaning → destroyed
     |           |         |
     +───────────+─────────+──→ failed ──→ cleaning, destroyed
```

Переходы проверяет машина состояний, недопустимый переход отклоняется. Создание машины идёт в фоне: ключ доступа, сервер, внешний IP, затем статус `ready`. Задача идемпотентна, поэтому повтор после сбоя не создаёт лишних ресурсов. При ошибках облака задачи повторяются с растущей паузой.

Очистка по расписанию удаляет стенды с истёкшим сроком и переводит в `failed` зависшие на создании. Заморозка и сообщение об инциденте продлевают срок жизни стенда. Срок, длительность заморозки и порог загрузки хранятся в базе и меняются из админки без перезапуска, каждое изменение пишется в журнал.

### Контроль ёмкости

Перед выдачей стенда сервис считает загрузку кластера по процессорам, памяти и диску с учётом размера новой машины. Если прогноз превышает порог, стенд не создаётся, а отказ записывается в журнал с состоянием кластера на тот момент. Если облако закрывает статистику гипервизоров, сервис считает загрузку по квотам и томам. Данные кешируются, но рядом с порогом кеш обновляется на каждый запрос.

### Доступ и проверки

Статических паролей нет. Для каждого стенда в облаке создаётся отдельная пара ключей, приватный ключ лежит в Redis с ограниченным сроком и удаляется вместе со стендом. Консоль в браузере работает через Apache Guacamole по SSH, VNC или RDP в зависимости от образа.

Проверка идёт без агентов. При создании машины cloud-init добавляет пользователя `inspector` с ключом сервиса и sudo только на нужные команды. Сервис подключается по SSH и выполняет шаги из YAML-шаблона в `config/check_templates`: пакеты, службы, порты, файлы, вывод команд, пользователи, процессы, HTTP и DNS, всего 13 типов. Шаги бывают обязательными и рекомендованными, общий результат роняют только обязательные. Отчёт хранит вывод и время каждого шага.

### Moodle

Основной канал работает по LTI 1.3. Сервис проверяет подпись токена по ключам платформы, одноразовые `state` и `nonce`, срок действия и разрешённые `deployment_id`. Курс и задание связываются с образом, размером машины и шаблоном проверки, отдельные параметры можно переопределить из Moodle. Если курс ещё не настроен, запрос сохраняется, и преподаватель настраивает его в один клик. Повторный вход студента открывает уже выданный стенд. Для систем без LTI есть REST-шлюз с той же логикой.

### Безопасность

Администратор входит по паролю с хешем Argon2, сессия хранится в HttpOnly cookie с защитой от CSRF. Ключи сервиса создаются при первом запуске и в репозиторий не попадают. Контейнеры работают от непривилегированных пользователей. В CI код и образы проверяют Ruff, Bandit, Gitleaks, pip-audit, npm audit и Trivy.

Серверная часть написана на Python 3.12 с FastAPI, SQLAlchemy и Celery, интерфейс на Next.js 16 и React 19.

## Как запустить

Потребуются Git, Docker с Docker Compose, make и доступ к «Кибер Инфраструктуре».

```bash
git clone https://github.com/vleypi/cloud-lab-manager.git
cd cloud-lab-manager
make bootstrap
```

Команда создаст `.env` и `config/pool.yaml` из шаблонов. В `.env` нужно указать данные для подключения к облаку (`OS_*`), почту администратора и хеш его пароля (`SUPER_ADMIN_*`), хеш выдаёт скрипт `backend/scripts/generate_admin_password.py`. В `config/pool.yaml` перечисляются проекты пула: UUID проекта, домена, сети и маршрутизатора.

```bash
make pool-validate
make up
```

После запуска интерфейс доступен по адресу http://localhost:8080, документация API по адресу http://localhost:8080/docs. Изменения пула подхватывает команда `make pool-reload`, остальные команды выводит `make help`.
