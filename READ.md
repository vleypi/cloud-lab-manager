КЕЙСОВОЕ ЗАДАНИЕ ДЛЯ ХАКАТОНА 
Кейс: Автоматизация работы с лабораторными стендами 
Описание: Создание безопасного веб-сервиса (шлюза оркестрации) для управления 
облачными ресурсами вручную и из системы LMS Moodle, с элементами 
автоматической проверки технических конфигураций в разворачиваемых средах на 
базе платформы «Кибер Инфраструктура» (далее - КИ). 
1. Введение и актуальность проекта 
Современное ИТ-образование требует практической подготовки в реальных 
инфраструктурных средах. Традиционный подход с локальной настройкой 
виртуальных машин на компьютерах студентов уходит в прошлое из-за ограничений 
производительности, сложности контроля со стороны преподавателя и отсутствия 
навыков работы с промышленными облаками. 
Перенос практики в облако решает проблему доступности ресурсов, но порождает 
новые серьезные вызовы: лавинообразный рост нагрузки на преподавателей по 
администрированию, необходимость жесткой изоляции сред учащихся, рутинную 
ручную проверку конфигураций и риск исчерпания ресурсов физического кластера. 
Данный кейс направлен на создание отказоустойчивого веб-сервиса, который 
безопасно распределяет облачные ресурсы «on-demand» (по требованию) на основе 
данных из LMS Moodle, контролирует утилизацию облака и автоматизирует проверку 
лабораторных работ. 
2. Проблематика 
При организации учебного процесса с использованием виртуальных лабораторий 
возникают следующие барьеры: 
1. Риски ИБ при динамическом администрировании: предоставление веб-сервису 
или LMS Moodle прав суперадминистратора для создания проектов «на лету» 
создает критическую уязвимость. Архитектурно правильное решение требует 
ухода от динамического создания доменов и перехода к управлению заранее 
подготовленным пулом изолированных проектов. 
2. Риск дефицита и перегрузки ресурсов облака: без жесткого контроля лимитов 
массовый одновременный запуск стендов студентами может утилизировать 
физический кластер до 100%, что вызовет отказ сервисов управления. 
Требуется строгий предиктивный контроль: запрет на запуск новых стендов при 
достижении критической отметки утилизации. 
3. Разрыв пользовательского опыта (UX): студенты тратят время на переключение 
между LMS и облачной панелью. При этом фиксированные тайм-ауты удаления 
стендов не подходят для всех типов лабораторных работ — преподавателю 
необходим гибкий инструмент управления временем жизни сред прямо в 
интерфейсе. 
4. Сложность разбора инцидентов: при возникновении технических проблем 
мгновенное автоматическое удаление стенда уничтожает «цифровой след» 
ошибки, делая невозможной консультацию со стороны преподавателя. 
5. Рутинная проверка: преподаватели тратят колоссальное количество времени на 
ручное подключение к ВМ для проверки выполнения практических заданий. 
3. Условия и предоставленная инфраструктура 
Участникам хакатона предоставляется доступ к тестовому контуру облачной 
платформы «Кибер Инфраструктура» (на базе OpenStack API). 
Концепция облачной инфраструктуры (КИ): 
Динамическое создание доменов и проектов сервисом запрещено из соображений 
безопасности. 
В КИ заранее созданы Домены (1 домен = 1 учебный курс). Внутри домена 
администрированием КИ подготовлен пул индивидуальных изолированных Проектов 
(Project) с собственными изолированными сетями (Neutron), объединенными с 
публичной сетью через маршрутизатор. 
Разрабатываемый веб-сервис выступает менеджером этого пула, распределяя 
свободные проекты студентам по запросу и возвращая их в пул после очистки. 
4. Этапы реализации проекта 
Для успешного выполнения задания разработка разделена на 5 последовательных 
этапов. Каждая группа функций должна быть реализована в рамках своего этапа. 
Этап 1: Ядро системы, сервис управления ресурсами и API КИ (Базовый MVP) 
Реализация логики поиска свободного предсозданного проекта в КИ для обеспечения 
принципа: «Один студент = Один индивидуальный проект». 
Контроль емкости: Разработка механизма валидации ресурсов. Перед развертыванием 
стенда сервис обязан запросить текущую утилизацию ресурсов КИ (CPU, RAM, 
Storage). Если запуск нового стенда приведет к превышению общей загрузки кластера 
КИ свыше 90%, сервис обязан заблокировать операцию, выдать предупреждение 
пользователю и залогировать событие. 
Реализация деплоя ВМ из существующих шаблонов (образов Glance) внутри 
выделенного проекта. 
Безопасный доступ: Использование нативных SSH-ключей, генерируемых внутри КИ. 
Использование статических паролей в коде или конфигурациях запрещено. 
Этап 2: Асинхронный жизненный цикл и Управление тайм-аутами 
Перевод длительных операций (развертывание, проверка, удаление) на асинхронные 
рельсы через очереди задач. 
Реализация автоматической деструкции (очистки) стенда через 2 часа после старта 
(параметр по умолчанию). 
Реализация режима «Техническая поддержка»: если студент заявляет о проблеме, 
автоматическое удаление замораживается на 24 часа для аудита преподавателем. 
Разработка UI-панели для администратора/преподавателя, где можно «на лету» 
изменить дефолтные параметры времени жизни лабы или заморозки. 
Этап 3: Движок автоматической SSH-проверки конфигураций 
Реализация безагентного подключения сервиса к ВМ студента по протоколу SSH с 
использованием нативных ключей КИ. 
Создание расширяемого движка тестов (на базе Ansible или кастомных 
структурированных скриптов). 
Движок должен уметь проверять: наличие установленного ПО, конфигурационные 
файлы, открытые сетевые порты в соответствии с паттерном конкретной лабы и 
возвращать детальный лог ошибок. 
Этап 4: Интеграция с LMS Moodle и маппинг пользователей 
Организация сквозного сценария: студент кликает в Moodle кнопку «Выполнить 
лабораторную работу №N» -> Moodle передает метаданные -> Сервис выделяет 
проект и разворачивает стенд. 
Гибкость интеграции: Полноценная реализация протокола LTI 1.3 является 
приоритетным (бонусным) решением. Допускается использование Moodle Web Services 
API (REST) или разработка собственного стабильного интеграционного 
шлюза/эмулятора запросов со стороны LMS, обеспечивающего точный маппинг 
пользователя на проект КИ. 
Этап 5: DevOps и единый стандарт DevSecOps 
Контейнеризация всех компонентов приложения (бэкенд, фронтенд, БД, очереди 
задач). 
Настройка запуска всего окружения одной командой через `docker-compose`. 
DevSecOps-стандарт: Обеспечение чистоты и безопасности кода. Обязательное 
использование линтеров, статических анализаторов безопасности, проверка на 
отсутствие секретов, записанных и запуск контейнеров от non-root пользователя. 
5. Технологический стек проекта (рекомендуемые 
Backend: Go или Python (Django/FastAPI). 
Frontend: React, Vue.js, желательно в стилистике КИ 
База данных: PostgreSQL (хранение состояний, пула проектов, логов и настроек). 
Очереди задач: Redis + Celery (для Python) или нативные воркеры/каналы с 
персистентностью (для Go).  
Инфраструктура: OpenStack API / КИ API / Ansible / кастомные bash (ssh) скрипты. 
Веб-сервер: Nginx.  
6. Критерии оценки решения 
Максимальный балл за проект: 100 баллов.  
Каждый из 10 критериев оценивается от 0 до 10 баллов.  
Оценка выставляется за каждый блок независимо. 
1. Работоспособность базового ядра сервиса совместно с API КИ (Этап 1) 
0-3: MVP отсутствует или нефункционально. ВМ не разворачиваются. 
4-7: ВМ разворачивается, но менеджмент пула проектов или логика очистки работают 
нестабильно. 
8-10: Полностью рабочий процесс выделения проекта из пула, корректный деплой по 
нативным SSH-ключам КИ, стабильная обработка крайних случаев (нет свободных 
проектов). 
2. Контроль емкости облака (Этап 1) 
0-3: Проверка нагрузки физического кластера полностью игнорируется. 
4-7: Контроль наличия проектов есть, но проверка утилизации физических ресурсов 
(ядер, ОЗУ, хранилища) носит декларативный характер. 
8-10: Жесткий предиктивный контроль. При утилизации >90% запуск блокируется, 
пользователю выводится понятное уведомление, а отказ фиксируется в логах 
администратора. 
3. Архитектура и управление асинхронными задачами (Этап 2) 
0-3: Синхронная архитектура. Долгие операции в облаке приводят к HTTP-тайм-аутам 
и блокируют UI. 
4-7: Задачи вынесены в фон, но Компонент управления состоянием (Машина 
состояний) работает нестабильно при сетевых сбоях, отсутствуют механизмы 
повторных попыток. 
8-10: Зрелая асинхронная архитектура. Корректная обработка и визуализация всех 
состояний («Выделение», «Развертывание», «Готов», «Заморожен», «Очистка»). 
4. Гибкий жизненный цикл и UI настроек (Этап 2) 
0-3: Тайм-ауты жестко захардкожены в коде. Логика заморозки отсутствует. 
4-7: Логика «2 часа на лабу / 24 часа на заморозку» работает, но параметры 
зафиксированы в конфигах, интерфейса управления для преподавателя нет. 
8-10: В интерфейсе преподавателя реализован удобный UI-инструмент для изменения 
лимитов «на лету». Изменения мгновенно применяются к Компоненту управления 
состоянием (Машине состояний) новых стендов. 
5. Качество движка SSH-проверки конфигураций (Этап 3) 
0-3: Проверка отсутствует или имитирована статичной заглушкой. 
4-7: SSH-подключение работает, но проверка ограничена выполнением одной простой 
Bash-команды без глубокого анализа конфигурационных файлов. 
8-10: Создан расширяемый движок проверок (Ansible или структурированные скрипты). 
Валидируется состояние ОС, ПО и сети, детальный лог ошибок выводится в 
интерфейс. 
6. Интеграция с LMS Moodle и маппинг пользователей (Этап 4) 
0-3: Интеграция отсутствует или заменена ручным вводом данных. 
4-7: Реализована базовая интеграция (REST API или эмулятор), сервис принимает 
данные, но разметка пользователей по проектам КИ иногда дает сбои. 
8-10: Бесшовная интеграция (промышленный LTI 1.3 или отказоустойчивый REST 
шлюз). Сервис безошибочно сопоставляет метаданные курса и закрепляет за 
студентом его персональный проект. 
7. Качество исходного кода и архитектурные паттерны 
0-3: Код написан хаотично, отсутствует обработка ошибок API, нет разделения 
приложения на слои. 
4-7: Код структурирован, читаем, разделен на логические модули. Присутствует 
документация в README.md. 
8-10: Код промышленного уровня, API задокументировано. Команды, написавшие 
идиоматичный, чистый и высокопроизводительный код на Go, получают максимальный 
балл. 
8. DevSecOps-стандарты безопасности 
0-3: Принципы ИБ полностью проигнорированы, в коде или конфигурациях 
присутствуют захардкоженные пароли/токены. 
4-7: Код прошел базовую проверку, критические секреты вынесены в переменные 
окружения, но автоматизированные инструменты проверки безопасности не 
интегрированы. 
8-10: Высший балл: в пайплайне или локально настроены линтеры и статические 
анализаторы, продемонстрировано отсутствие уязвимостей, контейнеры настроены на 
работу от non-root пользователя. 
9. DevOps: Контейнеризация и оркестрация развертывания (Этап 5) 
0-3: Проект запускается только в ручном режиме, зависимости не зафиксированы. 
4-7: Компоненты контейнеризированы, но запуск требует ручной настройки БД или 
очередей, скрипты автоматизации «сырые». 
8-10: Инфраструктура MVP разворачивается одной командой `docker-compose up --build`. Конфигурация полностью изолирована в `.env`, предоставлен понятный гайд по 
первоначальному наполнению пула проектов. 
10. Качество защиты проекта и презентация 
0-3: Презентация сделана небрежно, команда не смогла объяснить архитектурные 
решения. 
4-7: Команда рассказала о продукте, но не раскрыла технические детали: логику 
работы с API КИ, схему контроля лимита 90% и управление SSH-ключами. 
8-10: Профессиональная защита. Спикеры четко объяснили архитектуру шлюза, 
продемонстрировали схему Компонента управления состоянием (Машина состояний), 
обосновали ИБ-преимущества решения и уверенно ответили на сложные инженерные 
вопросы жюри.
